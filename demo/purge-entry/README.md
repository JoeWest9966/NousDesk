# 撕原件入口（3 套）

双击 `preview.html`（单文件，字体内嵌，196 KB，不用起 server）。默认**三套并排**，
顶部也能切到单套细看。`index.html` + `fonts.css` 是改的那份，改完跑
`python3 build-preview.py` 重新生成 `preview.html`。

## 背景：这不是"加删除功能"

先查了内核（`Nous` 仓 `content/new1/map/qrd3wh/server.js`），删除能力**早就有了**，
而且比"一键删"更稳：

| 动作 | 端点 | 语义 |
| --- | --- | --- |
| 归档 | `POST /v1/sessions/:id/archive` | 复印进 `data/archives/gen-*.sqlite` + 写墓碑，活库行不动 |
| 撕原件 | `POST /v1/sessions/:id/purge` | 验证复印件完整 → 事务 DELETE 九张表 + 墓碑记 purged |
| 打捞 | `POST /v1/archive/:id/restore` | 原样 INSERT 回活库 + 抹墓碑 |

桌面端**三处都已经接好了**：右键「更多 › 撕原件…」（副标题"先归档"）、确认框
（`archive_confirm.rs`，手输名字解锁）、归档库页的「撕原件 / 打捞」。
引擎还有四道守卫：忙 → 409、没归档 → 409、没完整复印件 → 409、有活分支 → 归档时就拦。

所以 `待开发.md` 第 1 条「给引擎加 `DELETE /v1/sessions/:id`」的前提是错的 —— 不是没有能力，
是**入口距用户七八下、跨两个页面**。三套方案争的只有这一件事。

## 三套方案

| # | 方案 | 一步做什么 | 代价 |
| --- | --- | --- | --- |
| 01 | 现状（尺子） | 右键「撕原件…」→ 撞 409「先归档」→ 归档 → 去归档库 → 选中 → 撕 → 手输名字 | 清一条会话 7–8 下、跨两页，没人愿意清第二遍 |
| 02 | 归档时问一句 | 归档确认框里加一个勾「归档后立刻撕原件」，勾了走完归档马上弹手输名字确认 | 归档框从此两种语义；勾选框是"顺手就勾了"的危险入口（但后面还有手输名字那一步兜着） |
| 03 | 右键一步到位 | 右键直接出「归档并撕原件…」，弹层里列出两步 + 手输名字解锁 | 菜单多一个红字危险项，若选它**必须撤掉旧的「撕原件…」**（同一个动作不能两个入口） |

## 三套共同的底线（不拿来做方案差异）

1. **手输会话名字才解锁红色按钮** —— 现有 `archive_confirm.rs` 的双层确认原样保留，一步到位也不能省这步。
2. **引擎四道守卫一个都不绕** —— 409 原文给用户看（`AGENTS.md`：原样透传，不改写）。
3. **归档先于撕原件** —— 顺序不能反；一步到位的那个动作内部也是先归档成功、再撕。

## 建议

**03**。清探针会话是个明确的、意图单一的动作（"这东西我不要了"），用户不该先撞一次 409
才知道有隐藏前置条件。把两步合成一个动作、在弹层里把两步**列出来**，比让用户自己猜顺序强。
手输名字那一步保住了"不可逆多走一步"的底线。

选 03 的话，按 `AGENTS.md`「同一个动作只留一个入口」，**旧的「撕原件…」从右键撤掉，
归档库页那条「撕原件」也撤掉** —— 危险动作只在右键这一个口子上。归档库页仍有「打捞」
（那是相反动作，不属于"同一个动作"）。
