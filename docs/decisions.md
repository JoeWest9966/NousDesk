
## 筛选器不许进树，窄窗的树只放类别（2026-11-23）

**背景**：980 宽时资源页只剩「列表 + 详情」两列，左树整块不画 —— 于是段切换、类别、垃圾站
三个入口一起消失。第一版把左树整体搬进中间列当第二层（`ResCol::Tree`），连同段按钮和
技能/提示词子开关一起搬了进去。

**代价**：段按钮一旦住在树里，它就有了「层级」的身份 —— 点一下 `内容` 等于把资源列换成
内容段的列表，用户看到的是「点筛选器整列被换掉」。2026-11-23 真机连指两次。

**现在的做法**：窄窗的资源列分两层，但**只有类别住在树里**：

- 条目层 = 筛选器（`内容/扩展` + `技能/提示词`，两行）+ 搜索 + 列表；`☰ 类别` 钻上去；
- 类别层 = 只有类别（真实类别 + 虚拟类别 + 状态桶）+ 垃圾站；`‹ 条目` 退回来；
- 段切换永远只换列表内容，不动 `narrow_col`。

**反悔点**：如果哪天窄窗能放下三条并列的窄列（比如最小宽度提到 1100），就退回宽窗那套，
把段按钮还给树；不要在两套之间加「有时在树里有时在列表头」的中间态 —— 那个中间态就是这次
出错的形态。

词表见 `docs/resources-vocabulary.md`（资源列 / 筛选器 / 类别 / 虚拟类别 / 条目 / 垃圾站）。

## 删掉「内容」这一层：资源页三段平铺（2026-11-24）

**背景**：资源页原来是「内容（技能 · 提示词）/ 扩展」两段，内容段里再挂一个技能/提示词
子开关。用户的判断（2026-11-24）：「内容这个没用，应该完全删掉」。

**为什么删得掉**：`内容` 那一层既不是一个私库、也不是一个视图 —— 引擎里只有
`NOUS_SKILLS` 和 `NOUS_PROMPTS` 两个独立仓（`rg NOUS_CONTENT` 全仓零命中），
Desk 把两者合在一个段里只是为了共用一套树 / 列表 / 详情。它带来的是：切技能与提示词要
点两次（先段、再子开关），而且「内容」这个词会让人以为背后有第三个东西（用户当场就这么
问过）。技能和提示词真正共用的部分（树的构建、行渲染、详情、发布）是**代码**共用的，
不需要一个界面上的父节点来表达。

**现在的做法**：`Section::{Skills, Prompts, Extensions}` 三个值平铺，各占一个槽位
（`Section::slot()` 是唯一的下标源，类别筛选与搜索词按槽位各存一份）。

- 宽窗：左树顶上三个段按钮（248 宽，三等分放得下）；
- 窄窗：列表头顶一行三个 pill（`技能 N | 提示词 N | 扩展 N`），第二行左边「+ 新建」、
  右边该段的工具（重载 / 垃圾站 / 类别只在扩展段）；**筛选器仍然不进树** ——
  2026-11-23 那条判据不变。

**顺手修的**：技能段拉不到清单时的占位文案错写成「正在等引擎回提示词清单」
（`RowKind` 传反了），删层时一并改对。

**代价**：宽窗窄窗的段按钮各自一套布局（跟以前一样两处都画）；加第四个段时两处都要动。
`counts()` 仍是唯一计数口径，不改。

**反悔点**：如果将来技能和提示词真的合成一个私库（一个仓两个子目录），那时「内容」才有
实体 —— 在那之前不要为了少点一次点击再加回中间层；也不要给段按钮加第二个维度
（比如段 + 子段），那正是这次删掉的形态。
